# Visual client milestone (Phase 40)

Drafted 2026-10-05 from an owner conversation. Status: **roadmap and
direction agreed; each phase still needs its own design approval** (handoff
rule 20). This milestone starts **after the current phase sequence** in
[Project Status](../PROJECT_STATUS.md) (35a–38c+) is finished, at the
owner's request. Art can be produced earlier, because it touches no code.
The sprite list is in the [sprite specification](2026-10-05-sprite-specification.md).

## Goal

Keep the browser client and its text, and add a visual layer over the same
authoritative Go server:

- a colorful tile map that updates as you move, with your class sprite
  walking on it, your camp shown when it is set up, and icons for what each
  room provides (water, forage and so on);
- an Ogre Battle 64–style battle screen that opens when a battle starts.
  It shows both 3x3 formations side-on, with sprites acting out each round.

Text players lose nothing. The narration stays the canonical record, and
every fact the visuals show is also available as text.

## Owner decisions (2026-10-05)

- Stay in the browser; no Unity or Unreal. Phones are served by the same
  web client (touch layout, installable web app; a store wrapper later if
  wanted).
- The map keeps the current web client look, upgraded. Inspired by MUME's
  mapper.
- Areas become denser, so a region is many rooms laid out as tiles. Tiles
  show guides for what a room provides.
- A sprite represents the player on the map, chosen by class. A camp sprite
  appears on the map when a camp is set up.
- An OB64-style battle screen, with OB64 as the main guide for layout and
  sprites. Original art only: OB64 assets are never copied or traced.
- **Other companies' camps are hidden.** Only your own camp is shown, plus
  your allied companies' camps (proposed).
- **Revisit for PvP:** camp visibility should later depend on lighting,
  terrain, and the company's skill at concealing its camp. Recorded as a
  deferred item in Project Status.
- Sprites are generated by another agent from the sprite specification.
  They are delivered in art sets matched to these phases.
- **Art direction:** mature, grounded high fantasy in the Lord of the
  Rings tradition, for a dangerous, unforgiving world. Not anime in any
  way. OB64's sprites are the reference the owner likes. Details are in
  the sprite specification.
- **Other players do not appear on the map for now** (your party members
  still do). Revisit later, alongside camp visibility.
- **Every room resource is wanted:** water, forage, shelter, herbs,
  firewood, fishing and game, with new mechanics where needed (40a and
  40a2).
- **A showcase area may be built** for the new features. Full world
  building comes later, once everything is in place.
- **No race or gender sprite variants for now.** Revisit with the races
  review.
- **An installable web app is enough.** No store app.
- **Travel** as proposed in 40d, and the battle screen opening
  automatically (40f), are approved. Allied companies on the battle
  screen follow the recommendation in 40f, pending approval.

## What exists today

- The web client has a canvas map window
  (`_datafiles/html/public/static/js/windows/window-map.js`). It draws
  visited rooms colored by biome, with map symbols and a hover tooltip. It
  updates from GMCP `Room` and loads visited rooms from `World.Map` on
  connect.
- Rooms already carry `mapsymbol`, `maplegend`, `biome`, `tags` and
  optional hand-placed `MapX/MapY/MapZ` coordinates. `internal/mapper` lays
  out rooms without coordinates and finds paths.
- GMCP `Company.Camp` reports the camp: whether one exists, its room, fire,
  resting state and progress.
- GMCP `Company.Battle` reports both sides' 3x3 cells, health, enemies,
  fallen members, retreat state, darkness and narrow ground.
  `window-combat.js` shows the setup grid.
- `internal/combatstream` already produces per-action combat events inside
  the server.

## Design constraints for every phase

- **The server stays authoritative.** The client draws only what the server
  sends. No visual may reveal hidden information: hidden exits, unvisited
  rooms, sneaking characters, other companies' private state, or other
  companies' camps.
- **Shared world time is never advanced** by walking, click-to-walk or
  battle playback. Animation never delays combat resolution: the server's
  round timing stays authoritative.
- **Text parity.** Every visual fact also appears as text (`look`, `camp`,
  the narration).
- **Graceful fallback.** A missing sprite falls back to a generic sprite,
  then to the current shape or letter rendering. A client with images off
  still works.
- **Help and tutorial.** Each player-facing phase ships help pages, keyword
  index entries and tutorial pointers, per `AGENTS.md`. Expected pages:
  - `help worldmap` (new in 40b, updated through 40d), with a see-also
    from GoMud's `help map`;
  - `help resources` (40a);
  - `help gathering` (40a2);
  - `help camp` (updated in 40b);
  - `help battlescreen` (40f–40g, linked from `help combat`);
  - `help travel` (40d).
- **Persistence.** Room resources are world data. Gathering pools (40a2)
  are durable world state that survives restart and copyover. Map
  preferences are per-viewer browser settings. No new player state is
  needed.

## Acceptance (milestone level)

Each phase's own design lists exact tests. Across the milestone:

- **Map and camp:** a player walking in the pilot region sees their class
  sprite move tile to tile. Resource icons match what `look` reports and
  what survival allows. Their camp appears and disappears with the camp
  state. Other companies' camps never appear.
- **Battle screen:** a battle opens the battle screen, plays every round's
  actions from structured events in step with the narration, and closes at
  the end with the correct outcome. A text-only client sees the same
  battle unchanged.
- **Phone:** the map and battle screen are usable on a phone-width
  screen.
- **Review gate:** every phase passes the project's testing and review
  gate.
