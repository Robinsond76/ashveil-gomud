# Ashveil–GoMud Integration Map

This map is based on the local source trees checked out on 2026-09-16. GoMud source paths are authoritative for implementation; the Python prototype is a read-only mechanics reference.

## Architecture decision

Ashveil will be an extension layer, preferably a compiled GoMud module plus focused engine-adjacent packages where the module API is insufficient. It will reuse GoMud rooms, movement parsing, character and item persistence, hired-mob creation, combat rounds, commands, events, and copyover mechanisms. It will not copy the Python session state machine or create a separate networking, inventory, room, or global-clock engine.

## Python prototype inventory

- `server/engine/game.py: GameSession` owns per-connection player, NPC party, campfire state, mount flags, and serializes player/party data through `persistence.py`.
- `server/engine/world_clock.py: WorldClock` is shared across sessions and owns day/night, weather, temperature, and subscriber notifications. Its shared-clock intent should be preserved, but its session-adjacent implementation should not be ported.
- `server/engine/systems/survival.py` provides party aggregation, hunger/thirst drains, stamina recovery, status display, and movement/combat penalties.
- `server/engine/systems/campfire.py: do_formation` persists member grid coordinates and provides formation management; current display is 2×3, not the target 3×3.
- `server/engine/combat/session.py: CombatSession` reads stored grid positions, has combatants with row/column fields, and renders/targets grids. `server/engine/combat/grid.py: assign_positions` enforces grid capacity.
- `server/engine/systems/mounts.py` implements inventory-based horse counting, ride/dismount behavior, and movement/combat hooks; it is prototype behavior only.
- `server/engine/persistence.py` uses SQLite and JSON player blobs. GoMud’s YAML/copyover conventions replace this persistence infrastructure.

## Travel state-machine requirements

The first TravelSession implementation must have `Traveling`, `Interrupted`, `Completed`, and `Cancelled` states; one authoritative transition owner; persisted origin/destination/profile/start/progress/cost checkpoint; and idempotent completion/cancellation. It must not mutate GoMud’s global round count or game time. Existing `RoomChange`, `NewTurn`, `PlayerDrop`, copyover contributors, and autosave are integration candidates, but exact attachment points require a dedicated Phase 5 design after the party and survival slices exist.

## Known risks and open decisions

1. Native `parties.Party` is global in-memory state and user-ID-only. Phase 2 must prove how hired mobs are owned, followed, saved, and reloaded before selecting the Ashveil expedition persistence model.
2. `usercommands.Go` currently recursively causes human party members in the same room to follow the leader. Ashveil travel interception must avoid duplicate movement, recursion, or placing members at the destination before arrival.
3. `Character.MiscData` is convenient for small character-owned values; complex shared party/cargo/travel state may need module-owned durable data and copyover support.
4. GoMud recognizes diagonal names in command scripting, but mapper and editor support have not been verified. Defer new direction work.
5. The prototype’s existing 2×3 formation is a design reference, not a migration contract; implement the approved 3×3 formation deliberately.
